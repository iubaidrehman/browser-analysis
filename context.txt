You are the principal software engineer responsible for building a research-grade
browser concurrency and automation performance benchmarking laboratory.

PROJECT NAME:
Browser Concurrency Research Lab (BCRL)

OBJECTIVE:
Build a controlled, reproducible experimental system that measures the performance
characteristics of different browser automation architectures at increasing levels
of concurrency.

The purpose is academic/engineering research.

DO NOT integrate with Walmart, retail websites, third-party purchasing systems,
anti-bot systems, CAPTCHA solving, queue bypassing, fingerprint spoofing,
residential/mobile proxies, or any mechanism intended to evade third-party
security controls.

The entire benchmark must operate against a locally hosted synthetic web
application that we control.

============================================================
1. CORE RESEARCH QUESTION
============================================================

Determine empirically:

"How do different browser execution architectures compare in startup latency,
memory consumption, CPU consumption, concurrency, throughput, P95/P99 latency,
failure rate, and scalability?"

We specifically want to understand the difference between:

A. One visible/headed Chromium process per worker
B. One headless Chromium process per worker
C. One persistent Chromium browser with many browser contexts
D. One persistent Chromium browser controlled through CDP
E. HTTP-only workers
F. Hybrid HTTP + browser workers
G. Optional CEF/off-screen Chromium
H. Different controller runtimes where useful

Do NOT assume any architecture is faster.

The benchmark must produce empirical evidence.

============================================================
2. IMPORTANT TERMINOLOGY
============================================================

The system MUST distinguish these concepts:

Logical Task:
    A unit of application work.

Worker:
    A runtime worker responsible for executing logical tasks.

Browser Process:
    An operating-system Chromium process tree.

Browser Context:
    An isolated browser environment inside Chromium.

Page:
    A browser page/tab.

HTTP Worker:
    A lightweight worker executing HTTP operations without a browser.

Browser Session:
    Persistent browser state associated with a logical task.

CDP Connection:
    A control connection to an already-running Chromium instance.

Do not use "task", "browser", "session", "context", and "page"
interchangeably.

Every benchmark result must make this distinction explicit.

7. BENCHMARK SCENARIOS
============================================================

Implement the following.

------------------------------------------------------------
SCENARIO A — HEADED CHROMIUM
------------------------------------------------------------

For each logical worker:

    launch independent Chromium
    create page
    execute workflow
    close browser

This is the intentionally expensive baseline.

Measure everything.

------------------------------------------------------------
SCENARIO B — HEADLESS CHROMIUM
------------------------------------------------------------

Same architecture as A.

Difference:

    Chromium runs headless.

Do NOT change the workflow.

This isolates the effect of graphical rendering/UI.

------------------------------------------------------------
SCENARIO C — PERSISTENT CHROMIUM + CONTEXTS
------------------------------------------------------------

Launch one Chromium browser.

Create multiple isolated contexts.

Example:

    Chromium
        |
        +-- Context 1
        +-- Context 2
        +-- Context 3
        +-- Context N

Each context must have independent:

    cookies
    localStorage
    IndexedDB

Measure:

    browser startup
    context creation
    page creation
    navigation
    workflow
    memory
    CPU
    throughput

------------------------------------------------------------
SCENARIO D — CDP
------------------------------------------------------------

Start Chromium independently.

Connect through CDP.

Measure separately:

    browser startup
    CDP connection
    context creation
    page creation
    workflow

The implementation must NOT claim that CDP is faster.

The benchmark exists to determine whether connection/reuse changes
the performance characteristics.

------------------------------------------------------------
SCENARIO E — HTTP ONLY
------------------------------------------------------------

Execute equivalent synthetic workflows using Go HTTP clients.

Use:

    connection pooling
    keep-alive
    bounded concurrency

No browser.

This establishes a lightweight baseline.

------------------------------------------------------------
SCENARIO F — HYBRID
------------------------------------------------------------

Implement logical workers where selected workflow operations are executed
through HTTP and selected operations through browser contexts.

Example:

    logical task
        |
        +-- HTTP
        +-- HTTP
        +-- browser
        +-- HTTP
        +-- finish

Make the escalation policy configurable.

Do NOT optimize against any third-party website.

------------------------------------------------------------
SCENARIO G — CEF
------------------------------------------------------------

OPTIONAL.

Do not implement CEF until all other scenarios work and produce valid results.

Use CEF only against the synthetic application.

Measure:

    initialization
    browser creation
    page creation
    navigation
    workflow
    memory
    CPU
    process count
    throughput

    |

    |

    |
Execution Engine

browser processes simply because the requested logical concurrency is 1000.

configuration values.
